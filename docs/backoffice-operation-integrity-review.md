# 後台單據操作修正與發布檢查

日期：2026-10-17（台灣時間）
基準：main `58a7ddc432c20aa5196f7e2ca2f2a2acb54f33a3`。

## 舊資料與影響

兩份 Stage 36 SQL 只建立／調整函式及權限；安裝時沒有執行既有訂單、叫貨單、廠商報價、庫存或帳款的回填、清除、重算。函式內的寫入只在使用者日後操作時執行。`vendor_quotes` 的資料與寫入流程不因這次更新而批次改變。

正式後台先前只讀核對過訂單及叫貨單列表、近期未完成單及一張展開的叫貨單，沒有正式寫入測試。這不是正式資料庫完整備份；不能將 UI 核對當成所有歷史資料都正確的保證。

發布前應使用既有備份功能匯出當前資料並保留 Supabase 備份。不要用正式單據執行到貨或收款測試。安裝及發布本身不應使舊單內容變動；日後按儲存或採用仍屬明確寫入。

## 已修正的已知問題

- 到貨／用途／新增報價等非同步回應固定原單據，切換到另一張單不會套錯回應或清除新表單。
- 同頁報價採用序列化；伺服器鎖住叫貨單並檢查雲端版本。採用報價與成本快照、移除品項與清除成本、到貨入庫與叫貨單到貨狀態均在同一資料庫交易完成，任一步失敗一起回復。
- 訂單編輯與快速收款／交付檢查畫面原始版本，拒絕用舊表單覆蓋其他裝置已儲存的版本。新增／編輯訂單的備註、客戶來源、收款、交貨也在同一交易內處理；不再先存交貨再單獨改完成狀態。
- 已到貨品項不能透過一般編輯更改價格、數量、採用廠商或移除。舊整單已到貨但缺少逐項欄位者，可保留原始快照修改整單備註；不補造到貨或庫存流水。若舊資料已有入庫流水但叫貨單仍未到貨，停止並提示先對帳，不自動再入庫或猜測更正狀態。
- 修改銷售訂單時，已叫貨／已到貨品項保留原廠商、價格、數量、規格及備註；有需求差異會回報，不自動變更廠商正在處理的內容。
- 草稿叫貨單已有採用報價而需求規格改變時，保留原報價快照並提示重新確認；既有整單與品項手寫備註不被來源文字覆蓋。明確改換草稿廠商仍會重置該品項舊報價與成本標記。
- 刪除的單據不會因延遲回應重新建立；未知雲端版本須先載入，沒有危險的無條件 upsert 備援。
- 背景同步不覆蓋正在編輯的草稿。版本衝突時，可按「重新從雲端抓取」確認替換目前單據；先備份當前草稿到本機，再載入雲端版本。備份失敗就停止替換；可按「下載草稿備份」匯出 JSON。備份在原瀏覽器，仍應下載保留。
- 雲端叫貨單／報價下載分頁讀至結束，任何分頁失敗不合併部分結果，避免誤以為資料消失。
- 核心 REST 與報價上傳／下載涵蓋回應內文的 30 秒逾時，寫入中斷提示結果待確認，不自動重送。
- Banner 新增保留尚未儲存的圖片、連結、焦點與空白列。
- 報價圖片保留類別／規格分欄。新明細以額外 JSON 欄位保存可見單價，與整機會計分攤分開；舊資料無法可靠推斷來源，不批改。規格長到最低可讀字級仍超出 A4 時，明確拒絕輸出被截掉的圖片；尚未加入自動多頁。

## 使用者需要注意的差異

| 情境 | 更新後行為 | 需注意 |
|---|---|---|
| 兩台裝置修改同單 | 後送出的舊版本被拒絕，保留草稿 | 核對差異後重新載入，再套用要保留的修改 |
| 已叫貨／到貨後改銷售規格或數量 | 不自動改廠商正在執行的品項 | 必須另向廠商確認取消／加減量或換規格 |
| 修改已到貨成本或品項 | 一般儲存會阻擋 | 要先對帳，另外設計明確的更正／退貨流程；不自動改歷史庫存 |
| 原單主內容或付款資料其中一步失敗 | 新的原子寫入整筆回復 | 不會出現主畫面成功卻只漏存部分欄位；逾時仍須查原單結果 |
| 舊單整機售價顯示為第一品項單價 | 未帶新單價欄位的歷史資料保留現值 | 不猜測清零，避免改掉真正手填的售價 |
| 已採用報價後修改草稿需求規格 | 原報價規格與價格保留，顯示警告 | 確認舊報價是否仍適用，再明確重新採用 |
| 更新後未重新整理的舊分頁 | Phase B 後舊寫入會被拒絕 | 手機和電腦都重新整理；先保留未存草稿 |

先前只讀核對看到既有單據的需求規格與採用規格存在差異。這可能是有意替代，沒有擅自改動；具體正式單號與內容留在私下核對紀錄，不放入公開儲存庫。

## 驗證與界限

`tests/operation-integrity.cjs` 執行實際前端函式／採購模組，模擬連點、回應延遲、切換單據、網路中斷、權限錯誤、草稿備份失敗、分頁失敗及新舊單價相容。

`tests/operation-integrity-db.cjs` 在隔離 PostgreSQL 執行真正 Stage 36 函式，下層交易效果以測試函式注入，驗證衝突、回復、權限、重複到貨及舊單保留。

`tests/operation-integrity-integration.cjs` 另載入儲存庫既有 Stage 22–27 的真實訂單／成本／入庫／用途函式與 trigger，驗證建立、採用、到貨、用途轉換、收款、交貨、完成訂單。測試使用臨時資料庫與假單據，沒有連線正式 Supabase。

目前上述測試由 Node 回報 58 項通過（包含父測試），0 失敗；包含 feedback／backup 既有回歸測試。3 支修改 JS 語法檢查及 git diff --check 通過。不是每一個後台按鈕都已逐一完成手機實機、列印或正式環境寫入驗收，也不是完整滲透測試。其他後台模組的跨裝置寫入不因此自動取得單據版本檢查，不能宣稱整站已沒有漏洞。

## 發布順序（不可跳過）

1. 保留正式備份及未儲存草稿。先核對 Supabase 已安裝的基礎函式與測試使用版本相容。
2. 由使用者於 Supabase SQL Editor 執行 `supabase-stage36-operation-integrity.sql`（Phase A）。只新增有保護的新入口，暫不關閉舊入口；現行前端可繼續使用。預檢失敗整份交易取消，不能略過錯誤繼續。
3. Phase A 成功後，再統一合併此前端與 SQL。確認 GitHub Pages 已部署，`admin.html` 的 shared/admin3/purchase-orders 三支快取版本均為 `20261017integrity36`。沒有 Phase A 時，新前端會顯示安全更新未安裝，停止寫入，不退回不安全的舊 API。
4. 使用者執行 `supabase-stage36-operation-integrity-enforce.sql`（Phase B）。關閉無版本檢查的舊 RPC 與叫貨單直接寫入；不動現有業務列。舊分頁需要重新整理。Phase B 未完成前，不能宣稱已封鎖舊分頁繞過版本保護。
5. 只讀核對正式單號、數量、廠商、價格、到貨及收付款狀態。真實 Safari、實體列印及多裝置實機驗證仍待發布後另行確認；不要為測試改動正式單據。

Phase A 後尚未部署時可暫停，現行版不受權限影響。Phase B 後不要直接回退舊前端，舊寫入會被拒絕；應保留資料並修正新版本，不應為恢復舊操作而開放匿名寫入。
