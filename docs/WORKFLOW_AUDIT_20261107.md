基準 main：`bff3aeed1f999576074f824609e3cfdf861bf392`。本輪只做可驗證的最小修正，不重寫系統、不以正式營運資料測試。

## 配單價格實際行為

- `.github/workflows/market-source-refresh.yml` 的 UTC cron `17 1,5,9 * * *` 對應台灣每天 **09:17、13:17、17:17**。這是預定啟動時間，GitHub 可能延遲。
- 正式配單目錄由 `scripts/sync-coolpc-catalog.mjs` 更新，來源為原價屋一般單品目錄；三家市場快照另行蒐集。欣亞／AUTOBUY 不會自動混成正式配單最低價。
- `data/dk-market-prices.json` 有覆寫機制，但目前 products 為空，因此沒有額外 DK 價格覆寫。將來啟用要另外驗證定價流程。
- 抓取、驗證、快照提交及 Pages 發布成功後，訪客重新整理才會讀到更新。來源失敗保留既有快照；商品突然少於原來 70% 也拒絕替換。已開啟的頁面沒有輪詢，不會自行跳價。
- 本機未送出的配單只保存商品 ID，重新整理會依最新目錄重算。已送出的線上配單則保存當時的單價、合計及目錄時間；正式後台訂單保存其單價，不會被目錄排程直接改寫。
- 本輪將過期提示改為 24 小時，目錄缺少合法更新時間時拒絕載入。這些價格仍是參考價，不表示現貨或 DK 最終成交價。

## 商品分類

每種零件先選「規格分類」，再選「品牌」，最後選商品。可直接搜尋型號繞過第一步。CPU 依插槽、主機板依插槽／DDR、記憶體依世代／容量、SSD 依容量、顯卡依晶片型號、散熱依高度、機殼依尺寸、電源依瓦數分類。只使用既有可判讀規格，未知項目明示待確認。

初次不展開全部商品；單一選單最多列 100 筆並提示繼續篩選。切換分類、品牌或搜尋不會移除已選商品；被篩掉的選擇會另顯示，總價與配單仍保留。既有相容性檢查和儲存格式不變。

## 本輪修正

1. 改到貨用途原本只改庫存與訂單，序號還留在舊訂單。新增採購單 trigger，同交易同步序號；已有組裝確認或售後狀態則整筆拒絕。
2. 序號售出／退款狀態原本只在已啟用掃碼驗收的訂單更新。保留舊訂單不強制掃碼，但未加入掃碼者正常結單仍會同步序號狀態。
3. 到貨序號登記 RPC 原本沒有核對真實到貨來源與累計數量。本輪在相同 API 簽章加上到貨品項、訂單用途及數量核對；維持舊分段到貨客戶端的正常呼叫，拒絕偽造或超量。
4. 配單送出加 20 秒逾時，避免無限停在儲存中；逾時仍可能已送達，不宣稱資料庫一定沒有寫入。

新增 SQL 只建立／調整函式及 trigger，沒有歷史資料回填、刪除或重算。正式安裝前先跑隔離驗證，安裝後核對 metadata／權限，不用真實單據試寫。

## 可以整合，但不可盲目合併

**網站購物車與核心財務尚未連動。** 網站單使用 `inventory` 上架數量，核心訂單使用 `inventory_items`／`inventory_ledger`。網站交付已扣上架數量，如果再盲目建立庫存出貨，可能雙扣；直接用售價減零成本又會高估毛利。

後續應以網站訂單 ID 建唯一關聯，核對每台上架主機的零件／成本來源，再提供「轉核心訂單／記帳」的單一入口與重送保護。現有正式商品未提供足夠的一對一映射，不能猜著回填或自動扣庫存。暫時沿用既有提示與複製資料方式，不把網站收款誤報為已自動入核心財務。

**掃碼只負責辨識及核對。** 原庫存流水、成本與結單維持一條寫入路徑，避免新增一套掃碼帳。

## 淘汰／保留判斷

- 已取消的 3D 預覽 `builder-preview.js`：現行與歷史頁面均無 script 引用，程式／測試也無呼叫者。本輪移除；Git 歷史保留。
- 舊問卷 `builder.js` 與舊照片目錄：現行頁面不載入，但仍有歷史 fixture／回歸測試依賴，暫不刪除或重構。
- `admin-v2.html`：舊網址轉址，保留可避免既有書籤失效。
- 手動庫存、手動成本、歷史查詢、作廢紀錄：仍處理盤點、更正、維修或歷史帳，不能只因已有自動到貨就移除。
- 兩個庫存資料層目前用途不同，不能直接合併表或刪舊表。

## 仍須後續處理

- 正式 GitHub Pages 發布之前連續兩次佇列失敗；這是發布阻礙，不能把 main 合併視同已上線。
